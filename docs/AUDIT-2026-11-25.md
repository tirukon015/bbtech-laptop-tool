# BBTech Laptop Tool: Full Project Audit and Gap Analysis

Date: 2026-11-25 · Branch `fix/itms-integration-e2e` (HEAD `5353597` + about 3,200 uncommitted lines across 36 modified and 21 new files)

Method: I read the source directly. I did not rely on earlier reports. Verified facts:

The audit did not cover real-device tests, UI automation or server tests, because none of them exist.

---

## A. Original goal

BBTech Laptop Tool is an internal preparation, testing and QC system. A laptop moves through these steps:
operator → detect → Hardware tests → Software checks/installs → QC inspection → final QC PASS/FAIL → ready for ITMS.
Records are kept offline on USB and synchronised to a central BBTech API (PostgreSQL). ITMS is a separate business system and stays separate.

## B. Current architecture (actual)

| Layer | Contents |
|---|---|
| `BBTech.Core` (net472) | Parsing, DeviceIdentity + matcher, encrypted QC journal (`QcRepository`), encrypted settings (`SettingsStore`, which holds operators, the session, the PIN, Wi-Fi and ITMS config), ITMS payload/connector/transmission, QR, **new (uncommitted):** `AppPermissions`, `AuditStore`, `UsbSyncQueue`/`BBTechApiClient`, `SoftwarePackage`, `ActivationProcessBuilder` |
| `BBTech.LaptopTool` (WPF, single EXE) | Detection (WMI + bundled tools), test panels, Home/Detect/Wi-Fi, **new dashboards:** Hardware, Software, QC, E-Commerce, profile picker, Settings window |
| Server / API | **Does not exist in this repository.** The client has only an API client class that points to a placeholder URL. |
| Tests | One xUnit project with 710 unit tests. There are no integration, UI, device, offline or release tests. |

## C. Completed (verified in code)

- Hardware detection (WMI, battery fallbacks, SSD health engine, HD Sentinel parsing), Detect view, exports, QR.
- Encrypted, append-only QC journal (`QcRepository`): history is preserved, and deletes are tombstones.
- Device identity: cleaned serial, UUID and board serial, placeholder rejection, hashing, conflict detection (`DeviceMatcher`).
- Interactive test panels: keyboard, touchpad, display, audio and microphone, camera, USB, Wi-Fi, Bluetooth, battery, storage.
- Per-test history (`RecordTest` creates a new record each run). Hardware/QC dashboards show the latest result and keep the history.
- ITMS HTTP connector: idempotency key, status-code classification, retry semantics. It is wired to the "Send to ITMS" dialog.
- Encrypted settings with an admin PIN hash (PBKDF2) and Wi-Fi provisioning.
- Windows and Office activation **status checks** use WMI `SoftwareLicensingProduct` and `OfficeSoftwareProtectionProduct`, which are legitimate Microsoft interfaces.

## D. Partially completed

| Feature | What exists | What is missing |
|---|---|---|
| Operator profiles + 1-hour session | `OperatorRecord.Departments[]`, `OperatorSession` with 1h expiry, profile picker | Admin profiles can be selected without any authentication. The workstation session file is plain JSON and can be forged. The legacy `CurrentOperatorId` fallback ignores expiry. Multi-department users are never asked and always land in their first department. |
| Permissions | `AppPermissions`, `CanPerform`, and checks in a few services | Every service check is `actor != null && !allowed`, so a **null actor passes**. The repository layer has no checks. Final QC does not check `qc.approve`. |
| Audit log | `AuditStore` and `AuditRecord` with a SHA-256 checksum | Plain JSON with an unkeyed hash, so it can be edited and re-hashed. A read error returns an empty list, and **the next write overwrites the whole log**. There is no hash chain. Several actions are not logged (operator selected, QC started, installation completed as a distinct event). |
| USB sync queue | State enum, `UsbSyncQueue`, `UsbSyncService` | Plain JSON, despite the "encrypted" doc comment. A read error wipes the queue on the next write. Records stuck in `Uploading` after a crash are never retried. The client is built with the **ITMS URL** (or the placeholder `https://api.bbtech.internal`) and no API key. A `null` server body is treated as **success, and every record is purged**. There is no independent verification step. |
| Software department | 6 interactive input panels, Office install/activation buttons | No audio or camera software checks. The driver check is display-only. The Office package is hard-coded (`SoftwarePackage.DefaultOffice()`). Master-config fetch is never called. |
| Software install | Elevated run of the installer, optional SHA-256 | The checksum is **optional**. The installer is searched for in the user's `Downloads` folder and run elevated without verification. It reports success if Office was already installed, even when the installer failed. |
| Activation | Status check plus `slmgr /ato` / `ospp /act` | The product key is concatenated into an elevated `cmd /c` string (injection risk if a key is ever supplied). |
| QC gate | QC checklist, Hardware summary, Final PASS/FAIL buttons | **Software results are not shown.** "Hardware ✓ Completed" appears if even one test exists. Missing or failed tests do not block PASS. There is no `qc.approve` check. The final decision is just another `RecordTest` row, so the latest one wins and anyone can overwrite it. There is no "ready for ITMS" state. |
| ITMS | Connector, transmission states, send dialog | Sending is **not gated on QC PASS**. |

## E. Missing

- Central BBTech API + PostgreSQL server (**BLOCKED BY EXTERNAL DEPENDENCY**: no server project, URL or key exists).
- Master data (models, required software, installers, test definitions) delivered from the server. The DTOs exist, but nothing consumes them.
- A dedicated, immutable QC decision record (with a snapshot of the results it was based on) and a "Ready for ITMS" status.
- Required-test definitions per department (what is "complete").
- Integration, UI-workflow, real-device, offline, server-failure, security and release tests.

## F. Security problems

| # | Problem | Where |
|---|---|---|
| S1 | **The Settings window is not PIN-gated.** Anyone can open it from Home or the sidebar and add users, change permissions, read Wi-Fi passwords and set the ITMS key. | `HomeView.Settings_Click`, `MainWindow.NavSettings_Click` |
| S2 | **Any technician can select "Touhidul (Super Admin)"** in the profile picker and gets `ALL`. | `UserProfileSelectView.ApplySelection` |
| S3 | A null actor bypasses every service permission check. | `SoftwareExecutionService`, `InspectionManager.DeleteTestResult` (called with no actor) |
| S4 | The forgeable plain-JSON session in `%LOCALAPPDATA%` restores any operator. | `SettingsStore.LoadWorkstationSession` |
| S5 | When there is no session, results are attributed to the *first active operator*, or to "Technician" or "QC Technician". | Hardware/QC/Software dashboards |
| S6 | Final QC does not require `qc.approve` and can be overwritten by any later record. | `QcDashboardView.RecordFinalQc` |
| S7 | Unverified installer from `Downloads` is run elevated. | `SoftwareExecutionService.ResolveInstallerPath` |
| S8 | Audit and queue files can be edited and re-hashed (no key). | `AuditRecord`, `SyncQueueItem` |
| S9 | Dead `DepartmentSelectView` still contains `EnsureOperator`, which creates or renames operators from free text. | `DepartmentSelectView.xaml.cs` |
| S10 | Inherent: the settings and journal keys are derived from an app constant, so someone with both the EXE and the USB can decrypt them. Real protection needs the server. | `AppSecret` |

## G. Cloud / server status

Nothing is connected. `BBTechApiClient` exists, with endpoints `/health`, `/v1/sync/upload`, `/v1/operators`, `/v1/config/master` and `/v1/software/packages`. There is no server and no URL setting, and the code reuses the ITMS URL by mistake. **BLOCKED BY EXTERNAL DEPENDENCY.**

## H. USB sync status

The state machine is real code and is invoked after every saved test, but it is unsafe (see D and S8). Data stays local because the URL is invalid. That is safe by accident, not by design.

## I. Hardware status

Cards exist and are wired: Battery, Storage/SSD, RAM, Display, Keyboard, Touchpad, Audio/Speaker (covers headphone L/R media), Microphone, Camera, Ports/USB, Wi-Fi, Bluetooth, Physical, Other.
Not present as separate cards: Mouse and Headphone. Results persist with history. Silent loss: if the device store fails to open or the identity conflicts, `RecordDepartmentTest` returns `null` and **nothing is saved and nothing is shown**.

## K. QC status

Covered in D. QC sees Hardware latest results (summary + list). It does not see Software, missing tests or the reasons for failures. The final decision is not a gate.

## L. ITMS status

`HttpItmsConnector` is the most mature integration: idempotent request IDs, retry and failure classification, and state stored in the journal. It is missing a QC-PASS precondition. Live end-to-end use depends on ITMS credentials (external).

## M. UI/UX problems

- The DepartmentSelectView text says "(Coming soon)", and the view itself is dead code.
- Multi-department users get no department choice and are dropped into their first department.
- Emoji and checkmark glyphs appear in QC status text ("Hardware ✓ Completed").
- Fallback names like "QC Technician" hide the fact that nobody is signed in.
- An E-Commerce dashboard is present, which duplicates the ITMS business side (scope question).

## N. Deployment problems

- The working tree **reverts the version from 1.2.0 to 1.1.0** (`Directory.Build.props`), which contradicts commit `5353597`.
- `dist\release.sha256.txt` (`81936950…`) **does not match** `dist\release\BBTech Laptop Tool.exe` (`C45E8E3A…`).
- Three copies of the EXE exist: `dist\`, `dist\release\` and `bin\Release\…` (plus `…old.exe`). The EXEs are stamped with commit `5353597`, but they were built from an uncommitted tree.
- Nothing shows "dirty build" or the build time in the app.

## O. Technical debt

- Dead code: `TestView` (the legacy inspection flow) and `DepartmentSelectView`.
- `new AuditStore(...)`, `new UsbSyncQueue(...)` and `new BBTechApiClient(...)` are constructed ad hoc in many places, with no single composition point.
- Department strings ("Hardware", "QC") are hard-coded everywhere. The team roster is hard-coded in `EnsureDefaultTeamProfiles`.
- `HasDepartment` treats "General", or a role name containing a department name, as membership.
- Two parallel result models: `SaveResult` (inspection-scoped) and `RecordTest` (department-scoped).

### Business rules chosen (please confirm)
1. Required Hardware tests are the 14 dashboard cards. Required Software items are the 6 input checks plus Windows activation. **Office activation is not required.** The QC checklist has 10 items.
2. PASS and SKIPPED both satisfy a requirement. SKIPPED is meant for hardware the laptop does not have.
3. QC FAIL can always be recorded. QC PASS needs everything complete with no FAIL. A newer QC decision supersedes an older one, and both are kept.
4. Final QC decisions cannot be deleted, even by an admin.
